# UI review — 2026-09-14 (the signed-in app)

This is the half that `DESIGN_REVIEW_2026-09-09.md` could not do. That document
ends:

> **The signed-in app was not seen.** The browser available to this review was
> not authenticated, so `/coach`, `/program`, `/progress`, `/log` and
> `/account` were read from their components and their CSS only. [...] The
> in-app half of this review should be redone with a screenshot of a real
> coach screen at 390px and at 1440px.

It has now been redone. Eighteen screens were rendered, measured and looked at
in **72 combinations** — every page at 390px and 1280px, in light and dark.

Nothing in the 09-09 review is repeated here. Its findings still stand and its
ordered list is still the right one for the marketing page.

## How this was measured, so it can be repeated

A harness (`web/harness/`, or the scratch build it came from) mounts the
**shipped page components** inside the app's real provider stack, with only
the network replaced. Fixtures carry production shapes read from the server
routes, and two data volumes: `sparse`, which is production exactly as it
stands today, and `full`, a year of training.

Three rules the harness obeys, each of them a bug it has already caused:

1. **Shapes come from routes, not from what a page appears to want.** The
   first fixture put `units` at the top level because the column is named
   `units`; the route wraps it in `equipment: { units, smallestPlatePair }`.
   Every weight on the Program page rendered with no unit and no plate
   readout, and the column widths were tuned against a page missing two
   things.
2. **Every api method is stubbed, not the ones a page is known to call.** An
   unanticipated fetch would otherwise hit the network, fail, and be reviewed
   in its error state - which looks exactly like a product defect.
3. **No real health data.** Injury and restriction fields are populated with
   invented text. The fields are real so the layout is honest; the content is
   not the athlete's.

### Three measurements in this review were confidently wrong

Recorded because it is the failure mode this repository keeps finding, and
because two of the three nearly became findings.

**A DOM background-walker put the Terms banner at 1.17:1.** The screenshot
shows dark text on light amber and is perfectly readable. The walker cannot
see gradients, alpha compositing or `::before` layers, which is most of this
stylesheet's grounds. *The 09-09 review records the same probe failing the
same way.* It was not reported.

**A pixel-sampling replacement put the nav at 2.97:1 "on rgb(0, 0, 0)".** A
light page has no black behind its nav. The sampler was reading pixels from
elements scrolled outside the painted area. Also not reported.

**A nav probe concluded that 5 of 9 destinations were unreachable on a
phone** - not scrollable, not hit-testable. It walked *up* from `.site-nav`
and never looked at `.nav-places`, the scroller *inside* it. Measured
correctly: `scrollWidth` 696 against `clientWidth` 359, scrolls to 337, and
the last item is hit-testable. **The nav is fine.** The stylesheet already
carries a comment about somebody making this identical mistake:

> An `overflow-x: hidden` on body was here briefly and has been removed. It
> was added to fix clipping that turned out not to exist.

What the numbers below rest on instead: **computed styles read out of the
running page**, and the theme tokens as `applyTheme` actually sets them -
verified to be running, 23 inline custom properties on `documentElement`, not
the pre-JS fallbacks in `:root`.

## What is already good, and should not be touched

**Nothing scrolls sideways.** 18 pages x 2 widths x 2 themes: `scrollWidth`
equals `clientWidth` in all 72. On a product with five-column tables and a
horizontally scrolling nav that is not luck.

**The dark theme's contrast is excellent.** Every token pairing clears AA with
room; the tightest is accent on `surface-2` at 5.11:1.

**The home page is the strongest screen in the product.** Hierarchy, a single
clear call to action, and a worked example conversation above the fold.

**The Progress charts are genuinely good.** Missed sets are drawn, not hidden,
and the page says so in a sentence at the top.

## What is actually wrong

Ranked. Every number was measured on a rendered page.

### 1. "Delete my account" is white on pink at 2.52:1

```css
.destructive {
  background: var(--error);
  color: #fff;        /* the only hardcoded color in the stylesheet */
}
```

`--error` in dark is `#ff7a7a`, a light pink. White on it computes to
**2.52:1** against a 4.5:1 requirement - verified from `getComputedStyle` on a
real `.destructive` button, `rgb(255,255,255)` on `rgb(255,122,122)`.

In light it is fine (5.62:1) because `--error` there is `#c62828`. One
hardcoded value, correct in one theme, is the whole defect: every other ink in
this system is a token that moves with its ground.

This is the most consequential button in the application and it is the one
that cannot be read.

### 2. The coach's own tables lose the weight column on a phone

The Program page was fixed today. **The same defect is still live in the
transcript**, where the coach writes the session as a four-column markdown
table the system prompt mandates:

| Movement | Sets | Reps | Weight |

At 390px the WEIGHT column is cut off mid-header ("WEI") and the loads read
`225`, `245`, `280`, `310` with the units clipped away. At 1280px it is fine.

This is the same table, in the same product, breaking in the same place, and
it is the surface where an athlete first reads their session. `sessionLayout.test.js`
was deliberately not widened to force this today, because the prompt's table
shape reaches the cached prefix, the judge's evidence matching and the safety
eval - it is a change that deserves its own commit and its own verification.

### 3. Log session is the weakest screen, and it is the one used every session

Four numeric inputs that do the same job - **Sets, Reps, Weight, RPE** - are
split across two rows at two different widths, because Sets is orphaned beside
the Movement field. They are one family and they read as two.

- **The Weight field carries no unit.** The athlete's units are known and on
  the page everywhere else.
- **"+ Add movement", the primary way to build a session, is a centered text
  link** - the least prominent control on a screen whose whole purpose it is.
  A six-movement day means tapping it five times.
- **"Remove" is also a link**, right-aligned next to a checkbox: a destructive
  action and a navigation affordance wearing the same clothes.
- One movement row is offered by default.

### 4. The Leaderboard is five paragraphs of policy with a leaderboard under it

Measured at 390px: **1,283 characters of prose before the first number.** The
lift selector is three full-width stacked buttons, the active one styled as a
primary call to action - so "which board am I looking at" is the loudest
element on the page, and "Leave the leaderboard", which deletes the athlete's
entry, wears the same gray as the two inactive tabs.

The policy text is good and it is all true. It is not the page.

### 5. The Account page says the same sentence twice

`consent.withdrawAnytime` - *"You can withdraw any of these at any time from
this screen..."* - renders at `Account.jsx:90` and again at
`ConsentPanel.jsx:149`, which Account mounts. The two are separated by a rule,
which makes it read as deliberate.

### 6. Every chart repeats an instruction that is false on a phone

*"Hover a point for the details, or use the arrow keys."* appears under all
four charts. On a touch device there is no hover and no arrow keys. With the
legend, that is twelve lines of identical chrome in one scroll.

### 7. The coach page has no `<h1>`

The only screen in the product without one, and the one an athlete opens most.

### 8. One measure, 760px, for prose and for data alike

`.page { max-width: min(760px, 100%) }` on every signed-in screen. It is a
good measure for reading. It is the wrong one for a five-column program table
and for a chart: on a 1680px display the Progress charts stay 670px wide with
920px of empty page beside them.

### 9. The recovery badge I added today fails AA in light

`.day-kind[data-kind='recovery'] { color: var(--secondary) }` at 10.88px.
`--secondary` in light is `#0093a0`: **3.70:1** on a card, **3.34:1** on the
page, **3.20:1** on `surface-2`. Needs 4.5.

Worth knowing *why* it was available to get wrong. `themes.js` solves every
theme's colors against their grounds to `AA_TEXT = 4.5` - except Miami, the
default, whose palette is a literal object that bypasses the solver. So the
one theme that ships to everybody is the one theme the guarantee does not
cover, and `--secondary` is the token where that shows. `--link` (`#00707c`,
5.26:1) is the pair that *was* solved for text.

The stylesheet's own header says *"The lowest ratio anywhere in the scheme is
5.60:1."* That is true in dark and false in light.

## The system underneath: measured

Union across all 72 renders, counting only elements with a box:

| | distinct values |
|---|---|
| **font-size** | **23** |
| padding | 33 |
| margin | 36 |
| gap | 17 |
| border-radius | 10 |
| font-weight | 4 |

Twenty-three font sizes is the finding, and the list says why:

```
10, 10.88, 11.2, 11.52, 12, 12.48, 12.8, 13, 13.12, 13.6, 14.08, 14.4,
14.72, 15.2, 16, 16.32, 17, 20, 23.2, 24, 32, 34, 56
```

`10.88`, `11.52`, `12.48`, `13.12`, `14.08`, `14.72`, `16.32` are not choices.
They are `em` multiplied by `em` - `0.85em` inside `0.8em` inside `1.02rem` -
and they appear because sizing is relative to whatever a component happened to
be nested in. Eight of the twenty-three sizes in this product were arrived at
by accident.

The 09-09 review found the declared scale collapsing in the middle
(`--text-headline` and `--text-body` both 17px, nothing between 32 and 17).
This is the other half of the same problem: **the scale exists and the app
does not use it.** A token nobody reaches for is not a system.

Ten radii, including `3`, `6`, `7`, `8`, `9.6`, `10`, `14`, and three
different ways of writing a pill (`50`, `980`, `999`).

## What I would do, in order

| # | Change | Effort | Risk |
|---|---|---|---|
| 1 | `.destructive` gets a token ink solved against `--error` in both themes | Minutes | None |
| 2 | Recovery badge off `--secondary`; give Miami's light secondary the solver every other theme gets | An hour | Low - it moves one color in the default theme |
| 3 | Merge the coach transcript's Sets and Reps columns, prompt included, with the judge and eval re-run | Half a day | **Medium** - it changes what the model writes |
| 4 | Rebuild Log session as one field family with units and a real "Add movement" button | Half a day | Low |
| 5 | A type scale and a spacing scale as tokens, and a guard that fails on a new ad-hoc value | A day | Low, but touches every file |
| 6 | Migrate screens onto the tokens, re-rendering each | A day | Low if 5 lands with the guard |
| 7 | Leaderboard: data first, policy in a disclosure; segmented control for the lifts | Half a day | Low |
| 8 | Chart chrome said once per page, not once per chart; drop hover wording on touch | An hour | Low |
| 9 | An `<h1>` on the coach page | Minutes | None |
| 10 | Let tables and charts opt out of the 760px measure | An hour | Low |

1 and 2 are accessibility defects and should go first regardless of the rest.
5 and 6 are the answer to "why does it look amateur": nothing is wrong with
the colors, and twenty-three font sizes is what the eye is actually reading.

## What still could not be checked

**Nothing was rendered against the production database.** Every screen here
is the shipped component with fixture data. Shapes were taken from the server
routes, but a route that returns something a fixture did not anticipate would
not show up in this review - the Leaderboard's `boards` array is one the
harness did not reproduce faithfully and its table was therefore not seen with
real ranks in it.

**No real device.** Headless Chromium at a 390px viewport is not an iPhone:
it has no software keyboard pushing the chat composer up, no rubber-band
scrolling, and no `hover: none` media differences beyond what was emulated.
